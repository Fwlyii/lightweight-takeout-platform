# 饿了么外卖系统 SRS 变更说明与审阅清单

## 1. 文档目的

本文档用于说明如何在学姐项目 SRS 的基础上，结合 2026 年《软件工程综合实践》要求、现有代码仓库能力和小组创新功能，对软件需求规格说明书进行增量修改。

当前 LaTeX 报告采用以下审阅约定：

- 原学姐 SRS 内容保留为黑色，作为当前基线。
- 本轮新增、替换和纠错内容统一显示为红色。
- 所有需要重绘或修改的旧图，在图内附加红色“审阅标记”。
- 红色需求与黑色基线发生冲突时，以红色需求为本轮拟议版本；最终定稿前须由小组确认并去除颜色。

## 2. 输入依据

### 2.1 今年课程硬性要求

来源：`/mnt/d/大三上/饿了么/26271学期-软件工程综合实践.md`。

必须纳入项目与文档的要求包括：

1. 项目周期为 2026-08-31 至 2026-09-20，共 3 周，小组规模为 3 至 4 人，本组为 4 人。
2. 第一周完成用户、商家、店铺、商品、购物车和基础订单等固定需求。
3. 第二周承接需求变更，新增测试并完成原功能回归测试，禁止通过大面积重构规避架构问题。
4. 第三周完成重构、交互完善、异常提示、数据校验、文档和交叉验收。
5. 必须全过程采用 TDD：先写失败测试，再实现，再通过测试，再重构并提交。
6. 核心业务接口测试覆盖率 100%，关键业务方法覆盖率不低于 90%。
7. 后端采用 Entity、Mapper/Dao、Service、Controller 分层；统一异常、统一响应和通用工具。
8. REST 接口应使用 `/api/v1` 版本前缀、资源名词 URI、正确 HTTP 方法与状态码；分页、筛选、排序使用查询参数。
9. 需要留存 Git 提交记录、测试报告、测试日志、需求变更记录、AI 使用说明和交叉验收材料。

### 2.2 图片功能分组

根据图片标注，功能按颜色归为以下模块：

| 颜色 | 模块 | 纳入范围 |
| --- | --- | --- |
| 橙色 | 营销与资产 | 优惠券叠加、充值会员、钱包、积分 |
| 绿色 | 个性化 | UI 主题换肤、记忆用户偏好 |
| 紫色 | 智能交互 | 智能导航、智能推荐菜品、上传图片识别菜品、语音点单 |

此外，本轮明确新增完整骑手端，不再沿用旧 SRS 中“不提供配送员业务流程”的范围说明。

### 2.3 会议中保留的补充创新

下列需求虽未全部写在图片中，但已在小组讨论中保留，纳入本轮 SRS：

- 商品详情展示热销榜、月售数量、折扣与限购提示。
- 商家故事与店铺场景图。
- “爆品团”“超抢手”等特价或热门商品推荐位。

好友拼单、通过 ID 互赠外卖不纳入当前范围。

## 3. 当前仓库基线审计

### 3.1 已有能力

- Spring Boot、MyBatis、Spring Security、JWT、WebSocket、MySQL 后端基础已存在。
- Vue 3 前端包含顾客、商家和管理员页面。
- 已有用户、商家、店铺、商品、购物车、地址和订单基础流程。
- 已有点赞、收藏、基础 AI 对话、消息通知和管理员总用户数/店铺数/营业额统计。
- 当前订单状态为：待支付、待接单、已接单、已完成、已取消。

### 3.2 与新需求的差距

- 权限表只有 `USER`、`BUSINESS`、`ADMIN`，缺少 `RIDER`。
- 订单没有待派单、待取餐、配送中、已送达、配送异常等骑手履约状态，也没有骑手关联字段。
- 没有评论、优惠券、钱包、积分、会员、主题偏好、语音识别、图片识别等实体与接口。
- 现有管理员看板只有三个总量指标，缺少时间维度、商家/菜品排行和用户消费分析。
- 当前 AI 对话可作为推荐入口复用，但还没有结构化推荐结果、图片识别和语音点单确认流程。

### 3.3 与今年课程规范的高风险差距

- 当前 Git 历史只有 1 次提交、1 个提交作者，不能证明 4 人全过程协作。
- 后端只有 2 个测试类、8 个 `@Test` 方法，远低于核心接口 100% 和关键方法 90% 的要求。
- 控制器路径使用 `/api/...`，尚未统一为 `/api/v1/...`。
- 仍存在 GET 修改数据和动词型接口，例如购物车 add/clear/remove、商品 delete、订单 submit。
- 当前 SRS 没有需求 ID 到测试用例、接口和提交记录的追踪关系。

这些问题不应仅在报告中描述，后续开发必须以真实代码、测试与 Git 记录补齐证据。

## 4. SRS 章节修改方案

### 4.1 引言与项目范围

需要修改：

- 将项目定位更新为“轻量级外卖服务平台（仿饿了么）”。
- 写明 3 周迭代周期、4 人团队、前后端分离和 TDD 约束。
- 区分第一周固定需求、第二周变更需求和第三周完善验收。
- 写明实际支付网关、人工客服、AI 转人工、好友拼单和 ID 互赠不在范围内。
- 写明 AI 推荐、识图和语音属于产品功能；AI 辅助编程仍须遵守课程限制并留存使用记录。

### 4.2 定义与缩略语

新增术语：骑手、配送任务、钱包流水、积分流水、优惠券叠加、会员权益、用户偏好、评论、数据看板、幂等、TDD、回归测试。

### 4.3 需求分析与涉众

原文“没有第 4 类涉众、不提供配送员业务流程”必须删除并替换。

涉众应扩展为：

- 顾客：点餐、优惠、资产、个性化、智能交互、评价、消费看板。
- 商家：店铺商品订单、活动、商家故事、经营看板、与骑手交接。
- 骑手：上线、接单、导航、取餐、配送、异常上报、历史与收入统计。
- 管理员：用户/商家/骑手审核，评论治理，优惠活动和异常订单监管，平台看板。
- 外部服务：地图定位、AI 推荐、语音识别、图片识别、对象存储；这些是系统依赖方，不是登录用户。

### 4.4 业务分析

业务域由原来的 6 个扩展为：

1. 用户与权限。
2. 商家与店铺。
3. 商品与库存。
4. 购物车与订单。
5. 配送履约。
6. 营销与资产。
7. 评论互动。
8. 个性化与智能交互。
9. 数据统计与看板。

需要新增订单履约状态机。建议状态如下：

`待支付 -> 待商家接单 -> 待派单 -> 待骑手接单 -> 待取餐 -> 配送中 -> 已送达 -> 已完成`

任何取消、拒单、超时和配送异常必须明确允许的发起角色、前置状态、资金/优惠券回退规则与消息通知。

### 4.5 功能性需求

需求按 ID 管理，建议优先级如下：

| ID 前缀 | 模块 | 建议优先级 |
| --- | --- | --- |
| BASE | 课程固定基础功能 | P0 |
| RID | 骑手与配送履约 | P0 |
| MKT | 优惠券、会员、钱包、积分 | P1 |
| REV | 评论与回复 | P1 |
| BI | 用户/商家/管理员数据看板 | P1 |
| PER | 主题与偏好 | P1 |
| PRD | 商品详情、热销榜、折扣限购、爆品推荐 | P1 |
| AI | 智能推荐、识图、语音点单 | P2 |
| MAP | 智能导航与地图 | 骑手基础导航为 P0，增强能力为 P2 |

P2 仍在 SRS 范围内，但不得挤占课程固定功能、骑手主链路和 TDD 证据建设。

### 4.6 非功能性需求

现有 SRS 只有系统架构和安全性，需要补充：

- REST API 与版本规范。
- TDD、覆盖率和需求追踪。
- 性能与并发验收基线。
- 事务一致性、幂等和重复接单保护。
- 外部服务超时、失败降级和重试边界。
- RBAC、隐私保护、日志审计和资产流水安全。
- 可维护性、可扩展性、兼容性和可用性。
- 数据统计口径与可解释性。

## 5. 功能模块详细变更

### 5.1 骑手与配送模块

核心用例：

- RID-01：骑手注册/申请并由管理员审核，授予 `RIDER` 权限。
- RID-02：骑手上线或下线；下线后不可接收新配送任务。
- RID-03：查看配送任务大厅或系统指派任务。
- RID-04：原子接单，同一任务只能绑定一名骑手。
- RID-05：查看商家和顾客必要的取送餐信息，敏感信息按需脱敏。
- RID-06：导航到店并确认到店、取餐。
- RID-07：导航到顾客地址并更新配送中状态。
- RID-08：确认送达，顾客确认收货后订单完成。
- RID-09：上报商家出餐慢、联系不上顾客、地址异常等情况。
- RID-10：查看配送历史、里程、完成单量和模拟收入。

关键规则：

- 骑手不得查看与自己无关订单的完整地址和电话。
- 骑手接单必须采用数据库条件更新、乐观锁或等效机制避免重复接单。
- 骑手不能越级修改订单状态。
- 已绑定骑手后，商家不能直接把订单改为“已完成”。
- 配送异常不得直接丢失订单，需要记录原因、时间、位置和处理结果。

### 5.2 营销与资产模块

- MKT-01：顾客查看可领取、可使用、已使用和已过期优惠券。
- MKT-02：结算时自动计算可用券，支持配置化叠加规则。
- MKT-03：默认假设同一订单最多使用一张平台券和一张商家券；是否允许会员券继续叠加需小组确认。
- MKT-04：模拟充值钱包，记录充值、消费、退款和调整流水，不对接真实支付，不支持提现。
- MKT-05：支付时可选择钱包余额；重复请求必须幂等，余额不得扣成负数。
- MKT-06：订单完成后发放积分，取消或退款时按规则回退；积分比例由后台配置，不在 SRS 写死。
- MKT-07：会员具有有效期和权益快照，会员价格/配送优惠需在下单时固化。

### 5.3 个性化模块

- PER-01：用户可选择主题颜色，主题需满足文字对比度和可读性要求。
- PER-02：主题和功能偏好保存到账号，跨设备登录后恢复。
- PER-03：系统记录用户主动设置的口味、忌口、价格区间和常购品类。
- PER-04：推荐使用偏好前必须允许用户查看、修改和清除；未授权时只使用当前会话信息。
- PER-05：每日幸运色只影响视觉主题，不得影响价格、排序权益或交易结果。

### 5.4 智能交互模块

- AI-01：根据用户偏好、历史订单和当前场景推荐商家/菜品，并展示推荐理由。
- AI-02：上传图片后返回候选菜品及置信度，必须由用户确认后才能加入购物车。
- AI-03：语音点单先转换为结构化点单草稿，展示菜品、数量、规格和价格，用户确认后才能提交。
- MAP-01：骑手获取取餐和送餐导航；顾客可查看配送位置或预计进度。
- AI/MAP 外部接口失败时必须回退到文字搜索、手动选餐和地址文本展示，不能阻断基础下单。
- 明确排除人工客服电话和 AI 客服转人工流程。

### 5.5 评价、商品展示与数据看板

- REV-01：仅已完成订单的顾客可评价，单个订单默认一条主评价，可编辑规则待确认。
- REV-02：评价包含评分、文字和可选图片；商家可回复但不可直接删除差评。
- REV-03：管理员可处理违规评价，所有隐藏/恢复操作记录审计信息。
- PRD-01：商品详情展示月售量、热销排名、原价/折扣价、库存和限购数量。
- PRD-02：“爆品团”“超抢手”展示活动时间、库存和优惠规则，售罄或过期后不可下单。
- PRD-03：商家故事和店铺场景图由商家维护；AI 生成图片必须标明为示意图，避免冒充真实店面。
- BI-01：顾客看板按月、品类和商家统计消费金额，并支持年度商家消费排行。
- BI-02：商家看板展示销量、营业额、热销菜品、订单状态和评价趋势。
- BI-03：管理员看板展示用户、商家、骑手、订单和交易汇总及异常订单数量。
- BI-04：看板只统计有效且未删除订单；取消单不计营业额，统计口径必须在接口文档中固定。

## 7. 数据模型影响

建议新增或扩展的数据对象：

- `rider_profile`：骑手资料、审核状态、在线状态。
- `delivery_task`：订单、骑手、取送地址快照、任务状态、时间戳、异常原因和版本号。
- `order_status_history`：订单状态变更前后值、操作者、时间和原因。
- `wallet_account`、`wallet_transaction`：余额与不可篡改流水。
- `point_account`、`point_transaction`：积分余额、来源、过期与回退。
- `coupon_template`、`user_coupon`、`order_coupon`：券规则、领取实例和订单核销快照。
- `membership`、`membership_plan`：会员有效期与权益。
- `user_preference`：主题、口味、忌口、价格偏好和授权状态。
- `review`、`review_reply`、`review_moderation_log`：评价、回复和治理审计。
- 商品表扩展库存、月售、折扣、限购；商家表扩展营业状态和商家故事。

订单必须保存商品价格、配送费、优惠、会员权益和支付构成快照，避免后续配置变化污染历史订单。

## 8. REST 接口影响

新旧接口最终应统一到 `/api/v1`。示例资源：

- `/api/v1/riders`、`/api/v1/delivery-tasks`。
- `/api/v1/wallets/{userId}/transactions`。
- `/api/v1/coupons`、`/api/v1/users/{userId}/coupons`。
- `/api/v1/orders/{orderId}/pay`、`/cancel`、`/confirm-receipt`。
- `/api/v1/delivery-tasks/{id}/accept`、`/arrive-store`、`/pickup`、`/deliver`、`/exceptions`。
- `/api/v1/reviews`、`/api/v1/reviews/{id}/reply`。
- `/api/v1/analytics/users/{id}`、`/merchants/{id}`、`/platform`。
- `/api/v1/recommendations`、`/recognitions/dishes`、`/voice-orders/drafts`。

业务动作允许使用 POST 子资源/动作路径，但 GET 不得修改数据。所有金额、库存、优惠核销、积分和抢单接口必须设计幂等键或并发保护。

## 9. TDD 与验收追踪

每个需求 ID 至少关联：

1. 一个正常场景测试。
2. 一个权限或异常场景测试。
3. 一个边界或并发场景测试。
4. 对应接口或业务方法。
5. 对应 Git 提交和测试日志。

重点测试包括：

- 两名骑手同时抢一单，只允许一人成功。
- 骑手越级更新状态被拒绝。
