# 1. 图 09：系统执行者分析图

目标文件：

`09-actor-analysis.png`

对应源图建议：

`drawio/09-actor-analysis.drawio`

## 1.1 图的目的

执行者是位于系统边界之外、通过系统获得业务价值或向系统提供服务的人或外部系统。

该图重点表达：

- 系统有哪些执行者；
- 执行者之间的泛化关系；
- 哪些执行者是独立执行者；
- 哪些是外部支撑系统。

本图主要是“执行者分析”，不要展开成完整的功能用例图。

## 1.2 执行者

### 游客

关系：

- 独立执行者。

主要交互：

- 浏览公开店铺；
- 浏览公开商品；
- 注册账号；
- 使用公开规则问答。

### 已登录用户

关系：

- 顾客、商家、骑手、管理员的通用执行者。

主要交互：

- 维护本人资料；
- 查看通知；
- 切换本人已经获得授权的角色。

### 顾客

关系：

- `已登录用户` 的特化角色。

主要交互：

- 管理配送地址；
- 管理购物车；
- 创建订单；
- 支付订单；
- 取消订单；
- 跟踪订单；
- 评价订单；
- 使用个人资产；
- 使用智能点餐。

### 商家

关系：

- `已登录用户` 的特化角色。

主要交互：

- 申请经营资格；
- 维护本人店铺商品；
- 处理本店订单；
- 回复评价；
- 查看经营数据。

### 骑手

关系：

- `已登录用户` 的特化角色。

主要交互：

- 申请配送资格；
- 上线 / 下线；
- 接单；
- 到店；
- 取餐；
- 送达；
- 上报配送异常。

### 管理员

关系：

- `已登录用户` 的特化角色。

主要交互：

- 准入审核；
- 账号治理；
- 内容治理；
- 配送异常处理；
- 平台统计。

### 外部服务

性质：

- AI、地图、对象存储等支撑执行者；
- 属于外部系统，而不是自然人。

主要交互：

- 通过受控接口提供生成能力；
- 提供导航能力；
- 提供媒体存储能力；
- 不直接改变核心业务状态。

## 1.3 必须保留的关系

四个业务角色都直接特化自：

`已登录用户`

即：

- 顾客 → 已登录用户
- 商家 → 已登录用户
- 骑手 → 已登录用户
- 管理员 → 已登录用户

不要为了布局需要制造：

- 管理员 → 骑手
- 骑手 → 商家
- 商家 → 顾客

等不存在的角色继承链。

## 1.4 重要业务规则

同一个自然人在通过审核后可以同时拥有多个业务角色。

但是：

- 每次请求仍按照当前角色授权；
- 同时还需要按照资源归属授权。

## 2.3 公共功能

### UC-COM-01 注册与登录

执行者：

- 游客；
- 已注册用户。

核心功能：

- 输入手机号和密码；
- 注册时校验字段格式及手机号唯一性；
- 安全哈希保存密码；
- 登录时校验凭证；
- 校验账号是否被禁用；
- 返回认证信息及用户角色列表。

注册成功后：

- 建立顾客身份。

登录成功后：

- 建立用户会话。

### UC-COM-02 个人资料与配送地址

执行者：

- 已登录用户。

核心功能：

- 查看昵称、头像、联系信息；
- 修改昵称、头像、联系信息；
- 新增配送地址；
- 编辑配送地址；
- 删除配送地址；
- 设置唯一默认地址；
- 校验当前用户和资源归属。

重要规则：

- 历史订单保存收货信息快照；
- 后续修改地址不得修改历史订单。

### UC-COM-03 角色切换与状态通知

执行者：

- 具有多个角色的用户。

核心功能：

- 查看本人已授予角色；
- 选择当前角色；
- 进入对应角色工作台；
- 接收订单、审核、配送等关键状态通知；
- 查看通知；
- 标记通知已读。

规则：

- 不允许选择未授予角色；
- 不允许进入未经审核的角色；
- 实时连接失败时仍可以通过通知列表查看消息。

目标文件：

对应源图建议：

`drawio/12-merchant-use-case.drawio`

## 5.1 UC-MER-01 商家申请与店铺状态

执行者：

- 顾客；
- 已审核商家。

主要过程：

- 用户提交商家资质申请；
- 审核通过后提交店铺基本信息；
- 店铺审核通过；
- 商家在以下状态之间切换：
  - 营业；
  - 休息；
  - 临时闭店；
- 顾客端同步展示店铺状态。

关键规则：

- 未审核用户不得进入商家工作台；
- 商家只能操作自己的店铺；
- 非营业店铺不能创建新订单；
- 商家审核和店铺审核是两个独立层次。

## 5.2 UC-MER-02 分类、商品与库存管理

执行者：

- 已审核商家。

主要功能：

- 查看本人店铺分类；
- 查看本人店铺商品；
- 新增分类；
- 修改分类；
- 删除允许删除的分类；
- 新增商品；
- 修改商品；
- 商品上架；
- 商品下架；
- 设置价格；
- 设置库存；
- 设置限购；
- 设置商品图片；
- 设置商品标签。

规则：

- 已被历史订单引用的商品逻辑下架，不物理删除；
- 库存统一通过业务服务管理；
- 下架商品不能下单；
- 售罄商品不能下单；
- 超过限购不能下单；
- 并发订单不能使库存变成负数。

## 5.3 UC-MER-03 商家处理订单

执行者：

- 订单所属店铺的商家。

主要功能：

- 查看本店订单；
- 接单；
- 拒单；
- 进入制作状态；
- 确认出餐；
- 创建等待骑手接取的配送任务。

规则：

- 商家不能处理其他店铺订单；
- 不能跳跃状态；
- 重复出餐不能生成第二个活动配送任务。

## 5.4 UC-MER-04 评价回复与经营看板

执行者：

- 已审核商家。

主要功能：

- 查看本店评价；
- 回复评价；
- 查看已完成订单量；
- 查看营业额；
- 查看客单价；
- 查看热销商品；
- 查看评分趋势；
- 可选获取 AI 数据摘要。

规则：

- 商家不能修改顾客原评价；
- AI 摘要只能解释统计结果；
- AI 不能修改原始经营数据。

## 6.1 UC-RID-01 骑手申请与工作状态

执行者：

- 顾客；
- 已审核骑手。

主要功能：

- 提交骑手申请；
- 提交必要资料；
- 查看审核状态：
  - 待审核；
  - 已通过；
  - 已拒绝；
- 审核通过后进入骑手工作台；
- 上线；
- 下线。

规则：

- 只有审核通过且上线的骑手才能接新任务；
- 有活动任务时不能直接下线。

## 6.2 UC-RID-02 查看可接任务与并发接单

执行者：

- 已审核且上线骑手。

主要功能：

- 分页查看待接单任务；
- 查看店铺；
- 查看目的地大致区域；
- 查看距离；
- 查看任务状态；
- 提交接单请求；
- 系统检查：
  - 身份；
  - 审核状态；
  - 上线状态；
  - 任务状态；
  - 当前任务上限；
- 原子绑定骑手。

并发要求：

两名合格骑手同时接同一任务：

- 只能一个成功；
- 失败请求不能覆盖成功绑定。

## 6.3 UC-RID-03 到店、取餐与送达

执行者：

- 当前任务绑定骑手。

主要功能：

- 查看取餐地址；
- 到店；
- 商家出餐后确认取餐；
- 查看必要收货地址和联系方式；
- 开始配送；
- 确认送达。

规则：

- 不能跳过取餐直接送达；
- 非绑定骑手不能操作；
- 骑手只在活动履约期间拥有必要敏感信息权限；
- 送达、取消或改派后收回权限。

## 6.4 UC-RID-04 配送异常、历史与导航

执行者：

- 当前任务骑手。

主要功能：

- 上报无法联系顾客；
- 上报地址错误；
- 上报餐品洒损；
- 上报其他异常；
- 填写异常说明；
- 等待管理员处理；
- 查看恢复配送结果；
- 查看改派结果；
- 查看终止结果；
- 查看本人历史任务；
- 打开外部地图导航。

规则：

- 骑手不能自行把异常任务直接设为取消；
- 地图不可用时仍然显示文本地址；
- 地图失败不能阻止其他配送状态操作。

# 8. 智能服务、营销资产和个性化

这些功能尤其会影响图 10 和图 11。

## 8.1 UC-AI-01 AI 客服与结构化智能点餐

执行者：

- 游客；
- 已登录顾客。

核心功能：

- 自然语言询问平台规则；
- 查询本人订单状态；
- 获取点餐建议；
- 系统识别用户意图；
- 使用经过审核的知识进行规则问答；
- 查询真实可售商品；
- 返回文本答复；
- 返回结构化商品候选卡片；
- 候选包含：
  - 商品标识；
  - 商品名称；
  - 商品价格；
  - 推荐理由；
- 顾客确认后调用普通购物车功能。

重要规则：

- AI 不能伪造商品；
- AI 不能伪造价格；
- AI 不能伪造库存；
- AI 不能伪造订单状态；

## 11.2 页面通用状态

所有关键页面需要考虑以下状态。

### 加载中

展示：

- 骨架屏；
- 或明确的加载指示。

交互：

- 防止重复提交产生副作用。

### 空数据

展示：

- 说明为什么没有数据。

交互：

- 根据场景提供：
  - 创建入口；
  - 搜索入口；
  - 返回入口。

### 表单错误

展示：

- 错误定位到具体字段；
- 使用可理解的提示文字。

交互：

- 保留其他合法输入；
- 不清空整个表单。

### 权限不足

展示：

- 明确无权访问；
- 不展示敏感数据。

交互：

- 引导返回当前角色首页。

### 状态冲突

展示：

- 数据已发生变化；
- 或操作已经被其他人完成。

交互：

- 刷新最新状态；
- 不覆盖已经成功的结果。

### 服务失败

展示：

- 简洁错误提示；
- 提供重试入口。

规则：

- 写操作只有存在幂等保护时才能自动重试。

# 12. 图 17：系统部署及外部依赖图

目标文件：

`17-system-deployment.png`

对应源图建议：

`drawio/17-system-deployment.drawio`

类型：

**UML 部署图**

## 12.1 总体架构

系统采用：

**浏览器访问的前后端分离架构**

核心技术：

### 前端

Vue 3

职责：

- 页面展示；
- 用户交互。

### 后端

Spring Boot

职责：

- 身份认证；
- 权限校验；
- 业务规则；
- 核心业务写操作；
- 外部服务适配。

### 数据库

MySQL

职责：

- 持久化业务数据。

### 外部依赖

由后端适配层统一封装，包括：

- AI 服务；
- 地图服务；
- 对象存储。

自动化测试：

- 使用可控 Mock / Stub。

## 12.2 强制架构关系

前端：

- 不得直接连接数据库；
- 不得持有外部服务密钥；
- 所有核心业务写操作必须经过后端。

后端：

- 负责核心业务规则；
- 负责权限；
- 负责外部服务调用。

数据库：

- 只能作为持久化层；
- 页面不能绕过业务服务直接修改订单、库存、资产、配送状态。

所以部署图至少要正确体现：

浏览器 / Vue 3
→ Spring Boot
→ MySQL

以及：

Spring Boot
→ AI 服务

Spring Boot
→ 地图服务

Spring Boot
→ 对象存储

不要画成：

Vue 3 → MySQL

或：

Vue 3 → AI 密钥 / 外部服务

这样的结构。

## 12.3 AI 服务接口

输入可能包括：

- 脱敏问题；
- 菜单候选；
- 图片；
- 语音。

输出：

- 文本答复；
- 结构化候选；
- 识别结果。

失败策略：

- 10 秒超时；
- 提示用户；
- 回退普通搜索或手工输入。

## 12.4 地图服务接口

输入：

- 店铺位置；
- 收货地点必要位置信息。

输出：

- 导航链接；
- 距离；
- 路线提示。

失败策略：

- 保留文本地址；
- 不阻断取餐；
- 不阻断送达；
- 不阻断异常上报。

## 12.5 对象存储接口

输入：

- 已经通过文件类型校验的图片；
- 已通过大小校验的图片。

输出：

- 文件标识；
- 可访问地址。

失败策略：

- 显示上传失败；
- 支持重试；
- 不影响无图片的核心流程。

## 12.6 外部服务降级原则

即使以下外部服务不可用：

- AI；
- 图片识别；
- 语音识别；
- 地图；
- 对象存储；

以下核心功能仍然应该工作：

- 普通登录；
- 搜索；
- 购物车；
- 订单；
- 文本地址；
- 状态管理。

# 14. 绘图时的总约束

绘图前必须依次做：

1. 先阅读本文件，确定当前编号图必须表达哪些需求。
2. 再查看课程第 10 章中对应类型 UML / 图形的标准和参考布局。
3. 可以借鉴第 10 章的表达逻辑和传统 UML 风格。
4. 不能直接复制第 10 章示例的具体结构和布局。
5. 根据本项目业务重新设计。
6. 不得因为参考图中存在某种关系，就给本项目凭空添加这种关系。
7. 图中出现的每个核心元素，都应该能够在 SRS 中找到依据。
8. 优先保持黑白、清晰、传统、易阅读。
9. 不追求装饰性和现代 UI 风格。
10. 复杂图优先分层，而不是把所有内容挤进一张图。
