需求讨论逐渐从功能清单转向具体业务场景：谁在什么前提下操作，成功后得到什么结果，失败时保留什么状态。实现阶段再把金额、库存、身份和状态规则落到服务端。界面调整后，成员会重新走登录、订单确认和返回路径，检查入口变化是否影响后续流程。

表中的日期取自提交和产物形成时间，可能和正式组会日期不同。下面按课程节点补充从需求分析到联调、验收和报告整理的过程，表中的仓库统计保持原有记录。

\subsection{分组与协作环境建立}
9月2日前后，成员完成仓库访问和本地环境检查，约定腾讯会议、微信群、飞书文档和 GitHub 各自存放的内容。大家先通读课程要求和初始工程，再结合熟悉程度安排前端、后端、数据库和测试主责。跨端问题由相关成员一起处理。

\subsection{需求分析与系统建模}
9月4日至8日，成员围绕四类角色、主要业务模块和履约流程整理《软件需求规格说明书》。总体架构图把参与者、前后端、数据库和外部服务放在一起，UML 总用例图逐项检查顾客、商家、骑手和管理员的职责。图\ref{fig:process-models}中的两类模型把文字需求整理成开发和验收都能使用的结构。

\subsection{阶段一开发与中期检查}
9月9日前后，阶段检查覆盖用户、商家、店铺、商品和订单。成员操作页面时同步查看请求参数、权限、状态变化和数据库记录。前后端理解不一致的地方先补写业务规则和影响范围，再一起调整页面、接口、数据结构和测试清单。

\subsection{分支开发与功能整合}
中期检查后，四名成员在各自熟悉的方向上并行推进，并围绕跨层业务联调。阶段任务在独立分支完成，经过自测和 Pull Request 检查后合入主分支。出现冲突时，修改页面和服务的成员一起核对规则、数据和测试结果。

\subsection{交叉验收、课程验收与报告整理}
交叉验收前，小组先用自动化测试和人工功能筛查检查自己的版本，并在缺陷表中记录复现条件和修复结果，方法见项目测试章节。9月16日的交叉验收面向其他小组，按对方提交的 SRS 和可运行版本逐项检查。内部缺陷表与交叉验收记录对应不同测试对象。

9月18日教师对本组项目进行课程验收。9月19日以后，成员根据反馈修正问题，并把需求、设计、实现、测试和协作材料放在一起检查。报告整理把仓库、共享文档、会议记录、缺陷表和运行截图串联起来，每个结论都对应相应产物。
