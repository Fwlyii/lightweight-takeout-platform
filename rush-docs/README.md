# rush-docs 文档说明

本文件夹集中保存“轻量级外卖服务平台（仿饿了么）”的软件需求、课程要求、四人模块分工和团队协作材料。建议所有组员先阅读老师的课程要求和最新版 SRS，再按照分工任务书与协作规范开展开发。

## 一、老师发送的课程要求

### `26271学期-软件工程综合实践.md`

这是老师发送的 **26271 学期《软件工程综合实践》课程要求原文**，不是小组自行编写的需求文档。文件规定了：

- 2026-08-31 至 2026-09-20 的三周实践周期；
- 3—4 人小组协作要求；
- 全过程 TDD，先写失败测试、再实现、再重构；
- 核心业务接口测试覆盖率 100%，关键业务方法覆盖率不低于 90%；
- Spring Boot 分层、Vue 组件化及 REST 接口规范；
- Git 过程记录、AI 使用说明、需求变更记录和交叉验收材料；
- 三周各阶段的功能、迭代、重构和验收要求。

该文件应作为课程规则和最终验收的最高依据之一，开发前和提交验收材料前都要重新核对。

## 四、团队协作与合并规范

### `团队协作与合并规范.md`

这是结合老师要求和当前代码仓库实际问题编写的团队执行规范。它统一以下事项：

- Git 分支、提交、Pull Request 和合并顺序；
- TDD 红—绿—重构证据以及测试门禁；
- `/api/v1`、HTTP 方法、响应体、错误码和分页格式；
- Java、Vue、数据库、金额、时间、状态枚举和命名约定；
- 模块边界、共享文件修改和数据库迁移方式；
- 联调环境、配置、密钥和测试数据；
- 冲突解决、紧急修复、最终集成和交叉验收清单。

所有成员开始并行开发前应共同确认并执行这份规范。规则发生变化时，应先更新文档和接口契约，再修改代码。

### `业务规则与代码边界.md`

记录价格、限购、购物车、登录身份、订单状态和商家评分等关键概念的单一事实来源。新需求开发前先查这份文档，完成后运行 `./scripts/check-architecture.sh`，避免旧接口、魔法数字和前端伪造身份回流。
