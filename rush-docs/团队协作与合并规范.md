# 轻量级外卖服务平台团队协作与合并规范

版本：1.0  
日期：2026-09-03  
适用仓库：`elemo` 代码仓库  
适用人员：四名项目成员

## 1. 文档目的

本规范用于解决四人并行开发中常见的接口不一致、字段重名、数据库脚本互相覆盖、公共文件冲突、测试被跳过、配置只在个人电脑可用以及最后一天集中合并等问题。

所有成员在开始模块编码前应共同评审本规范。若后续决定与本文不同，必须先形成书面决策并更新本文件、SRS 或接口契约，不能只在聊天中口头通知。

本文依据：

- 老师发送的 `26271学期-软件工程综合实践.md`；
- 最新编译 SRS；
- 当前仓库中的 Spring Boot、MyBatis、Vue 3、Spring Security、JWT、MySQL 和现有测试代码；
- 当前项目实际存在的接口、配置和协作风险。

## 2. 不可违反的课程要求

以下内容来自老师课程要求，优先级高于组内个人习惯：

1. 全过程执行 TDD：需求行为 → 失败测试 → 业务实现 → 测试通过 → 重构。
2. 禁止先完成业务代码后集中补测试；测试必须包含有效断言。
3. 核心业务接口测试覆盖率 100%，关键业务方法覆盖率不低于 90%。
4. 每次需求变化必须增加相应测试，并执行原有功能回归测试。
5. 后端保持 Entity、Mapper/Dao、Service、Controller 分层。
6. Controller 只负责接收请求、校验参数和返回结果，核心业务规则放在 Service。
7. 接口使用 `/api/v1` 版本前缀；GET 只查询；资源 URI 使用名词；分页、筛选、排序使用查询参数。
8. 使用正确的 HTTP 方法、HTTP 状态码和统一响应体。
9. 保留四人的真实 Git 贡献、测试报告、测试日志、需求变更、AI 使用和交叉验收材料。
10. 禁止临交作业前集中上传代码，禁止通过一次性大面积重构逃避需求变化。

## 3. 当前仓库已发现的合并风险

这些问题不是抽象建议，而是当前代码中已经存在的风险。新增模块不能继续扩大差异；公共基础修复应先于四个模块的大规模联调。

| 风险 | 当前表现 | 统一处理方式 |
|---|---|---|
| API 版本不统一 | 多数控制器仍为 `/api/...` | 新接口统一 `/api/v1/...`；旧接口迁移必须有兼容期和回归测试 |
| GET 修改数据 | 购物车 add/clear/remove、商品 delete、订单 submit 等使用 GET | 新代码禁止；旧接口按测试保护逐步迁移为 POST/PATCH/DELETE |
| 响应解析不统一 | 前端 AI 服务兼容多种响应结构 | 全项目冻结为 `{ success, code, message, data }`，前端不再猜测多种格式 |
| HTTP 状态不明确 | 全局异常可能只返回业务失败体 | 统一业务错误与 400/401/403/404/409/422/500 的映射 |
| 前端后端地址硬编码 | `request.js` 写死服务器 IP | 统一读取 `VUE_APP_API_BASE_URL`，仓库只提交 `.env.example` |
| Token 键名冲突 | 同时出现 `token` 和 `authToken` | 统一使用 `token`，只能通过认证工具读写 |
| 路由重复 | `/merchantProfile` 重复声明 | 每个路由 path/name 唯一，新增前执行路由检查 |
| 测试默认被跳过 | Maven 属性中存在 `<skipTests>true</skipTests>` | 测试命令显式使用 `-DskipTests=false`；公共 PR 移除默认跳过配置 |
| 前端缺少测试命令 | `package.json` 只有 serve/build | 首个前端功能 PR 前统一测试框架与 `npm run test` 命令 |
| 数据库无迁移顺序 | 存在多个初始 SQL，新增表没有统一机制 | 使用有序迁移文件，禁止成员直接覆盖共享初始化 SQL |
| 测试证据不足 | 当前只有少量测试类和测试方法 | 每个需求至少补正常、异常/权限、边界/并发测试 |
| 公共对象容易冲突 | 状态枚举、错误码、安全配置、路由均是多人修改热点 | 指定公共文件维护人，其他成员通过独立 PR 提交变更请求 |

## 4. 开发基线与环境必须统一

### 4.1 固定技术版本

- 后端：Java 17、Spring Boot 3.4.6、MyBatis Spring Boot Starter 3.0.4。
- 构建：优先使用仓库内 `elm_bk/mvnw`，不要依赖个人安装的 Maven 版本。
- 前端：Vue 3.2、Vue Router 4、Element Plus 2；依赖版本以 `elmclient/package-lock.json` 为唯一依据。
- 前端安装依赖使用 `npm ci`，禁止在未讨论的情况下使用 `npm update` 或混用 yarn/pnpm。
- 数据库：全组使用同一 MySQL 大版本、字符集 `utf8mb4`、排序规则和时区。
- 编码：源代码、SQL、JSON、CSV 和 Markdown 统一 UTF-8，禁止提交带乱码的文件。

### 4.2 环境配置

- 后端地址、数据库账号、JWT 密钥、AI 密钥、地图密钥全部通过环境变量配置。
- 前端 API 根地址固定从 `VUE_APP_API_BASE_URL` 读取，不能在组件或 service 中写死 IP。
- 只提交 `.env.example`，不提交真实 `.env`、密码、Token、个人服务器地址或第三方密钥。
- 建议每人准备独立数据库，例如 `elm_<姓名缩写>`，不要多人直接修改同一个开发库。
- 联调环境数据库只能通过已评审迁移脚本更新，不能在数据库管理工具中临时手改后不留记录。

### 4.3 启动和验证命令

在仓库根目录执行：

```bash
cd elm_bk
./mvnw -DskipTests=false test
./mvnw -DskipTests=false package
```

```bash
cd elmclient
npm ci
npm run build
```

前端测试框架确定后，还必须执行统一的 `npm run test`。任何成员不能使用“我本地 IDE 能运行”代替这些可重复命令。

## 5. Git 分支和提交规范

### 5.1 分支模型

- `main`：始终保持可构建、可测试、可演示；禁止直接开发。
- `develop`：四个模块的日常集成分支；通过合并门禁后再阶段性合入 `main`。
- 功能分支：从最新 `develop` 创建，完成后通过 Pull Request 合回 `develop`。
- 紧急修复：从出问题的目标分支创建 `fix/...`，修复后同时同步到仍在开发的相关分支。

分支命名：

```text
feat/mkt-wallet
feat/per-theme
feat/ai-recommendation
feat/rev-review
feat/bi-merchant-dashboard
feat/rid-delivery-task
test/mkt-coupon-concurrency
fix/order-idempotency
docs/api-contract
refactor/shared-exception
```

禁止使用 `new`、`test1`、`我的分支` 等无法说明用途的名称。

### 5.2 模块前缀

| 模块 | 分支/提交/需求前缀 |
|---|---|
| 公共基础功能 | `BASE` |
| 骑手与配送 | `RID` |
| 营销与资产 | `MKT` |
| 个性化体验 | `PER` |
| 智能交互 | `AI` / `MAP` |
| 评价 | `REV` |
| 数据看板 | `BI` |
| 商品展示增强 | `PRD` |

### 5.3 TDD 提交序列

同一个需求至少形成可识别的红—绿—重构记录：

```text
[MKT-01][RED] test: 添加重复钱包支付失败测试
[MKT-01][GREEN] feat: 实现钱包支付幂等处理
[MKT-01][REFACTOR] refactor: 提取资产流水创建逻辑
[MKT-01][DOCS] docs: 更新钱包支付接口与测试结果
```

要求：

- RED 提交中的测试应当因需求尚未实现而失败，不得通过禁用、空断言或伪造结果制造记录。
- GREEN 只实现使测试通过的必要代码，避免夹带其他模块的大量修改。
- REFACTOR 不改变已经确认的外部行为，重构前后测试都必须通过。
- 每位成员使用自己的真实 Git 姓名和邮箱，不能代替别人提交或伪造时间。

### 5.4 同步频率

- 开始工作前获取并合入最新 `develop`。
- 每完成一个可独立测试的小需求就提交，不等到整个模块结束。
- 功能分支最长不要脱离 `develop` 超过一个工作日。
- 每天至少进行一次集成，尽早暴露接口和数据库冲突。
- 不允许在最后一天一次性合并四个长期分支。

## 6. 文件归属与并行修改规则

### 6.1 模块所有者

每个创新模块指定一名主责人。主责人负责需求、表结构、Service、接口、页面、测试和文档的完整闭环，但不获得绕过评审直接修改公共契约的权限。

| 模块 | 主要后端对象 | 主要前端区域 |
|---|---|---|
| MKT | wallet、point、coupon、membership、order quote/payment | 资产中心、会员页、结算优惠区 |
| PER | user preference、theme、consent | 主题切换、偏好设置 |
| AI/MAP | recommendation、assistant、recognition、voice、map adapter | AI 对话、推荐、识图、语音、导航 |
| REV/BI/PRD | review、reply、moderation、analytics、product statistics | 评价、商品详情、三类看板 |
| RID（公共） | rider、delivery task、status history、exception | 骑手工作台、配送进度 |

课程要求中的“后端架构与 TDD、后端业务与数据库、前端与验收文档、测试与迭代适配”属于横向职责；四个创新模块属于纵向业务分工。建议每名成员同时承担一个业务模块和一个横向职责：

| 横向职责 | 对所有模块的责任 | 不能代替模块主责人完成的事情 |
|---|---|---|
| 后端架构与 TDD | 维护分层、公共异常/响应、测试基类、覆盖率门禁，审查 TDD 证据 | 不能替其他三人补写全部测试或独自决定业务规则 |
| 后端业务与数据库 | 维护数据字典、迁移顺序、事务与索引规范，审查 SQL | 不能直接覆盖其他模块迁移或代替模块成员解释业务逻辑 |
| 前端与验收文档 | 维护 request、路由和公共组件，汇总接口/验收材料 | 不能在没有接口契约时自行猜字段，也不能代替全组完成交叉验收 |
| 测试与迭代适配 | 维护回归集合、缺陷清单、变更影响和最终冒烟流程 | 不能把测试集中到最后补写，也不能替代每位成员的模块测试责任 |

这样既保留“一人一个创新模块”的清晰所有权，又符合老师对架构、数据库、前端文档和测试迭代职责的要求。

### 6.2 公共热点文件

以下文件或区域一次只能由一名指定维护人修改：

- `pom.xml`、`package.json`、`package-lock.json`；
- `SecurityConfig`、JWT 过滤器、全局异常处理、统一响应类和错误码枚举；
- 前端 `request.js`、认证工具、主路由和全局状态入口；
- 订单状态、配送状态、支付状态等公共枚举；
- 初始化 SQL、迁移目录和公共测试配置；
- SRS、OpenAPI 总文件和最终验收索引。

需要修改公共文件时：

1. 在群内或 Issue 中声明修改目的、字段/接口影响和负责人。
2. 先提交一个只处理公共基础的独立 PR。
3. 公共 PR 合入后，其他模块更新自己的分支再继续开发。
4. 禁止四个人分别复制并修改一份相同的公共类，最后手工拼接。

## 7. 后端代码统一规范

### 7.1 分层职责

- Entity：仅表达数据库实体和映射，不包含控制器或外部服务调用逻辑。
- DTO：接收请求，配置 Bean Validation；禁止直接用 Entity 接收外部写请求。
- VO/Response：返回页面需要的数据，避免返回密码、密钥和内部审计字段。
- Mapper/Dao：只负责数据访问，不编写跨领域业务流程。
- Service：事务、资源归属校验、状态机、金额、库存、资产和并发规则。
- Controller：路径、HTTP 方法、认证信息、参数校验、Service 调用和 HTTP 响应。
- Adapter/Client：地图、AI、语音、图片、对象存储等第三方调用。

禁止：

- Controller 直接调用 Mapper；
- 前端提交任意 userId 后，后端不校验就按该 userId 操作；
- Service 返回与 HTTP 强耦合的页面对象；
- 把资金、积分、库存和优惠变更拆成多个无事务保护的写操作；
- 捕获所有异常后统一返回 HTTP 200。

### 7.2 命名

- Java 包全部小写；类用 PascalCase；方法和变量用 camelCase；常量用 UPPER_SNAKE_CASE。
- Entity 使用单数名，例如 `WalletAccount`；表名使用小写 snake_case，例如 `wallet_account`。
- 请求对象采用 `CreateXxxRequest`、`UpdateXxxRequest`；返回对象采用 `XxxResponse`。
- Service 方法以业务语义命名，例如 `acceptDeliveryTask`，不要使用 `doIt`、`handleData`。
- 一个业务概念只保留一个英文名称：顾客统一 `customer`，商家统一 `merchant`，骑手统一 `rider`，店铺统一 `store`。若旧代码使用 `business`，新旧映射必须在接口文档说明，不能在同一新模块混用。

### 7.3 事务与并发

- 创建订单、支付、取消、退款、优惠券核销、积分发放、库存预占和骑手接单必须在 Service 层定义事务边界。
- 余额和积分使用条件更新或版本号，更新后检查受影响行数。
- 一单一骑手、一单一评价、幂等键等规则必须由数据库唯一约束兜底，不能只靠前端按钮禁用。
- 不在事务中调用耗时第三方服务；采用明确的记录、调用和补偿策略。
- 同一资源的锁顺序全组统一，避免模块交叉调用产生死锁。

## 8. REST 接口契约

### 8.1 路径和方法

- 新接口统一以 `/api/v1` 开头。
- URI 使用复数资源名词和 kebab-case：`/api/v1/delivery-tasks`。
- GET 查询，POST 创建，PATCH 局部修改，DELETE 逻辑删除。
- 支付、取消、接单、送达等明确业务动作允许使用 POST 子资源/动作路径，例如：

```text
POST /api/v1/orders/{orderId}/payments
POST /api/v1/orders/{orderId}/cancellations
POST /api/v1/delivery-tasks/{taskId}/acceptance
POST /api/v1/delivery-tasks/{taskId}/delivery-confirmations
```

- 禁止新增 `/getXxx`、`/addXxx`、`/updateXxx`、`/deleteXxx` 风格接口。
- 搜索、分页、过滤和排序使用 Query 参数，不用 POST Body 模拟普通查询。

### 8.2 统一响应体

所有 JSON 响应固定为：

```json
{
  "success": true,
  "code": "OK",
  "message": "",
  "data": {}
}
```

失败示例：

```json
{
  "success": false,
  "code": "COUPON_ALREADY_USED",
  "message": "优惠券已使用",
  "data": null
}
```

- `success` 只使用布尔值。
- `code` 是稳定、可测试的英文大写业务码；前端不能依赖中文 message 判断业务。
- `message` 用于用户提示，不返回堆栈、SQL、密钥或内部路径。
- `data` 成功时返回业务数据，无数据时为 `null` 或明确的空对象/空数组；同一接口必须固定。

### 8.3 HTTP 状态码

| 状态码 | 使用场景 |
|---|---|
| 200 | 查询或业务动作成功 |
| 201 | 资源创建成功 |
| 204 | 删除成功且无需响应体；若统一响应体则使用 200，项目内二选一后固定 |
| 400 | 请求格式、类型或基础参数错误 |
| 401 | 未登录、Token 缺失或失效 |
| 403 | 已登录但角色或资源归属无权访问 |
| 404 | 资源不存在 |
| 409 | 状态冲突、重复提交、并发抢单失败、唯一约束冲突 |
| 422 | 格式正确但业务规则不满足，例如余额不足、优惠券不适用 |
| 500 | 未预期服务端错误，响应不得暴露内部信息 |

### 8.4 字段、金额和时间

- JSON 字段统一 camelCase。
- ID 统一使用后端生成的 `Long`；前端不得自行生成正式业务 ID。
- 金额：Java 使用 `BigDecimal`，MySQL 使用 `DECIMAL(12,2)`；禁止使用 float/double 处理金额。
- 数量、库存、积分使用整数，后端校验上下限。
- 时间接口统一使用 ISO 8601 并带时区偏移，例如 `2026-09-03T14:30:00+08:00`。
- 状态字段返回稳定英文枚举码，例如 `WAITING_RIDER`，中文显示由前端映射。
- 布尔字段使用 `enabled`、`active`、`used` 等明确名称，不用 0/1 字符串。

### 8.5 分页格式

请求统一为 `?page=1&size=20&sort=createdAt,desc`：

- `page` 从 1 开始，默认 1。
- `size` 默认 20，最大 100。
- 返回固定为：

```json
{
  "items": [],
  "page": 1,
  "size": 20,
  "total": 0,
  "totalPages": 0
}
```

### 8.6 幂等

- 创建订单、充值、支付、取消、退款、资产核销和发放接口使用 `Idempotency-Key` 请求头或等价唯一业务键。
- 后端保存幂等记录和原响应；相同用户、相同操作、相同键的重试不产生第二次副作用。
- 前端按钮防抖只改善体验，不能替代后端幂等。

## 9. 前端统一规范

### 9.1 API 调用

- 所有请求经过 `elmclient/src/utils/request.js`，组件内禁止新建 axios 实例或写完整服务器 URL。
- 每个领域在 `src/services` 下建立一个 service 文件，页面只调用 service。
- `request.js` 统一处理根地址、Token、401、超时和通用错误；业务 service 不再兼容多种随意响应格式。
- 上传文件由浏览器生成 multipart Content-Type，禁止手工写错误 boundary。

### 9.2 登录状态

- Token 存储键统一为 `token`。
- 用户概要统一为 `userInfo`，字段结构由登录接口契约定义。
- 所有组件通过统一认证工具或状态模块读取登录状态，不直接散落读取 localStorage。
- 退出登录必须同时清除 localStorage、sessionStorage、用户状态和私有缓存。

### 9.3 路由和组件

- route path 使用 kebab-case，例如 `/merchant-orders`；route name 使用 PascalCase，例如 `MerchantOrders`。
- path 和 name 都必须唯一；合并前检查重复路由。
- 公共导航、空数据、加载、错误、确认弹窗和分页组件集中复用。
- 页面组件不直接实现金额计算、优惠资格和订单状态转换等核心规则。
- 样式尽量使用公共设计变量；不得为一个模块全局覆盖 Element Plus 类名导致其他页面变形。

### 9.4 用户提示

- 统一使用一个消息组件，不混用 `alert`、不同 Toast 和页面自制提示。
- 加载、成功、无数据、业务失败、网络失败和权限失败必须有不同状态。
- 不向用户展示后端堆栈、对象序列化结果或“undefined”。

## 10. 数据库迁移规范

### 10.1 唯一迁移入口

建立并统一使用：

```text
elm_bk/src/main/resources/db/migration/
```

迁移文件命名：

```text
V202609030901__create_wallet_tables.sql
V202609030902__create_user_preference.sql
V202609030903__create_review_tables.sql
```

即使暂未接入 Flyway，也必须按文件名顺序执行并记录。是否引入 Flyway 只能通过公共基础 PR 决定。

### 10.2 禁止行为

- 禁止直接修改已在其他成员数据库执行过的迁移文件；修正使用新迁移。
- 禁止每个成员提交一份完整数据库导出覆盖别人内容。
- 禁止使用 `DROP DATABASE`、无条件 `DELETE` 或不可恢复清表作为普通迁移。
- 禁止把个人测试账号、真实电话、真实地址和密钥写入正式迁移。
- 禁止依赖“先手工建一列程序才启动”的本地隐式步骤。

### 10.3 表结构统一

- 表名、列名 snake_case；主键统一 `id`；外键命名 `{resource}_id`。
- 所有表明确主键、非空、唯一、默认值和必要索引。
- 需要逻辑删除的表统一字段名与含义，不允许 `deleted`、`is_delete`、`status=-1` 混用。
- 所有资产、订单和配送关键状态变化保留时间与操作人，不物理删除审计流水。
- 每个迁移 PR 必须提供升级说明、测试数据影响和回滚/补偿方案。

## 11. 状态机和跨模块规则

订单、配送、支付、优惠券和评价状态属于公共契约。任何人不得在自己模块中私自添加另一套字符串。

- 后端使用一个受版本控制的枚举/状态转换服务。
- 数据库保存稳定英文码，前端通过统一映射显示中文。
- OpenAPI、SRS、测试和数据库取值必须一致。
- 每次状态变更校验当前状态、当前角色和资源归属。
- 禁止前端直接提交任意目标状态让后端保存。
- 关键状态记录原状态、新状态、操作者、原因和时间。
- 取消、拒单、超时和异常必须同时明确库存、优惠券、积分、钱包和配送任务如何处理。
- 状态表变更必须由订单、骑手、营销和评价/统计负责人共同评审。

## 12. TDD、测试与证据

### 12.1 每个需求的最小测试集

每个需求 ID 至少包含：

1. 正常场景。
2. 参数或业务异常场景。
3. 未登录、角色错误或资源越权场景。
4. 边界场景。
5. 涉及资产、库存、接单、评价唯一性时的重复/并发场景。
6. 对既有相关功能的回归测试。

### 12.2 测试层次

- 单元测试：金额规则、状态转换、优惠资格、推荐解析等纯业务逻辑。
- Mapper/数据库测试：唯一约束、条件更新、聚合口径和迁移脚本。
- MockMvc：路径、HTTP 方法、状态码、统一响应、参数校验、认证和授权。
- 前端组件测试：渲染、输入、确认、错误状态和权限分支。
- 端到端冒烟：注册登录、浏览加购、下单支付、商家处理、骑手配送、确认评价。

### 12.3 测试数据

- 使用固定、可重复的数据工厂或 SQL fixture，禁止依赖成员个人数据库的残留数据。
- 测试之间相互隔离；测试顺序改变后仍能通过。
- 时间相关测试使用可注入 Clock，禁止依赖“当前时刻刚好未过期”。
- 第三方 AI、地图、语音和对象存储使用 Mock/Stub，不将真实网络稳定性当成自动化测试前提。

### 12.4 合并门禁

PR 合并前必须同时满足：

- 新测试的 RED 证据可追踪，最终测试全部通过。
- 后端 `./mvnw -DskipTests=false test` 与 package 成功。
- 前端 `npm ci`、统一测试命令和 `npm run build` 成功。
- 没有跳过、注释或仅打印无断言的测试。
- 核心接口和关键方法达到课程覆盖率要求。
- OpenAPI/ApiFox、数据库迁移、README 和需求追踪已同步。
- 至少一名非作者成员完成代码审查和本地验证。

## 13. Pull Request 规范

### 13.1 一个 PR 只解决一个可描述问题

推荐规模是一个需求 ID 或一个公共基础改动。禁止将格式化整个仓库、升级依赖、修改数据库、重写接口和实现多个模块混在同一个 PR。

### 13.2 PR 描述模板

```markdown
## 需求
- 需求 ID：MKT-01
- 目标：

## 接口与数据变更
- API：
- 数据库迁移：
- 是否破坏兼容：否/是（说明迁移办法）

## TDD 证据
- RED 提交：
- GREEN 提交：
- REFACTOR 提交：
- 测试命令与结果：
- 覆盖率：

## 联调与回归
- 前端影响：
- 其他模块影响：
- 已验证场景：

## AI 使用说明
- 是否使用：
- 使用位置及人工修改/核验：
```

### 13.3 审查重点

- 是否符合已冻结的接口与数据契约。
- 是否把业务逻辑放在正确层。
- 是否存在越权、重复扣减、负库存、状态越级或隐私泄露。
- 是否覆盖异常、权限、边界和并发。
- 是否夹带无关文件、个人配置、构建产物或密钥。
- 作者能否解释关键断言、事务和架构选择。

## 14. 合并顺序

同一批跨模块功能严格按照下列顺序合并：

1. 需求 ID、状态机、接口契约和错误码。
2. 数据库迁移及对应数据库测试。
3. 公共基础代码：响应、异常、认证、分页、幂等、测试基类。
4. 被依赖的后端领域能力。
5. 依赖这些能力的其他模块后端代码。
6. 前端 service、状态管理和公共组件。
7. 业务页面和路由。
8. 端到端测试、接口集合和验收文档。

例如“钱包支付后看板显示实付金额”，必须先冻结订单金额快照，再合并营销资产，最后合并看板，不能由看板成员自行猜测钱包字段。

## 15. 冲突处理规则

### 15.1 普通文本冲突

1. 先理解双方修改意图和对应需求 ID。
2. 保留两边必要行为，不能直接选择 `ours` 或 `theirs` 覆盖另一方。
3. 解决后运行冲突文件涉及模块的测试及完整回归。
4. 由冲突双方共同检查最终 diff。

### 15.2 数据库冲突

- 不修改已合并迁移编号；新增更晚的修正迁移。
- 两个模块新增同名列或不同类型的相同概念时暂停合并，先更新数据字典。
- 迁移执行一半失败时，记录当前版本，按补偿脚本恢复；禁止直接删库掩盖问题。

### 15.3 接口冲突

- 已被其他模块或测试使用的字段不能静默改名。
- 必须破坏性修改时，先新增新字段或新版本，保留兼容期，再迁移调用方。
- 后端、前端、OpenAPI 和 Mock 数据在同一个联调窗口同步更新。

### 15.4 公共配置冲突

- 依赖升级、SecurityConfig、CORS、JWT、request.js、路由等冲突由公共维护人最终整合。
- 合并后必须重新验证登录、权限、文件上传、跨域和所有模块入口。

## 16. 常见意外情况处置

### 16.1 某成员分支长时间落后

- 暂停新增功能，先备份工作并同步最新 `develop`。
- 小步解决冲突，每解决一个领域就运行相应测试。
- 若差异过大，将未完成工作拆成更小 PR，禁止一次性强推覆盖集成分支。

### 16.2 `develop` 被合坏

- 立即停止后续合并，记录最后一个成功提交。
- 通过新的修复 PR 恢复，不改写共享分支历史。
- 补充一个能捕获该问题的回归测试。
- 禁止对共享分支执行 `git push --force`。

### 16.3 测试在一人电脑通过、他人失败

- 比较 Java、Node、MySQL 版本、环境变量、时区、字符集和迁移版本。
- 使用 `npm ci` 和 Maven Wrapper 重新验证。
- 若仍不一致，将复现步骤和环境差异记录到 Issue，不能用跳过测试合并。

### 16.4 第三方 AI 或地图不可用

- 启用统一 Mock/降级适配器。
- 基础搜索、购物车、订单和文本地址配送继续工作。
- 不临时把个人密钥提交到仓库救急。

### 16.5 发现密钥或个人信息被提交

- 立即禁用或轮换密钥，并通知全组停止使用。
- 从当前代码移除并改为环境变量；检查构建产物和日志。
- 是否需要清理 Git 历史由全组评估后执行，不能由个人擅自强推重写历史。
- 记录事件、影响范围和修复结果。

### 16.6 需求临时变化

- 先新增变更记录：原需求、新需求、原因、影响模块和验收标准。
- 先写失败测试，再做最小实现；保留旧功能回归测试。
- 通过策略、状态机或适配器扩展，避免为一个变更重写整个模块。

### 16.7 两人修改了同一业务规则

- 暂停双方 PR，回到 SRS、接口契约和测试确定唯一规则。
- 选择一个实现作为主线，另一个实现中有价值的测试或逻辑通过新提交迁移。
- 不把两套规则同时保留在不同 Controller 或页面中。

## 17. 每日集成流程

每位成员每天结束前执行：

1. 更新本地 `develop`，解决当天冲突。
2. 运行本人模块测试及受影响回归测试。
3. 运行后端 package、前端 build。
4. 提交当天最小完整改动并推送。
5. 更新需求—测试—接口—提交追踪表。
6. 在群内说明：已完成、待评审、阻塞项、是否修改公共契约。

每天由一名轮值集成人检查：

- `develop` 是否可构建。
- 新迁移是否可从空数据库顺序执行。
- OpenAPI 与前端 service 是否一致。
- 是否出现重复路由、重复错误码、重复状态枚举。
- 是否有成员分支超过一个工作日未同步。

## 18. 最终合并与验收流程

### 18.1 冻结安排

- 最终验收前至少预留一个完整工作日停止新增需求，只允许修复阻断问题。
- 冻结后禁止升级主要依赖、重命名大量文件或重新设计整个数据库。
- 所有 PR 必须在最终打包前完成评审，不把未审查分支直接复制进主分支。

### 18.2 最终合并检查

- 从全新目录克隆仓库，禁止依赖旧缓存。
- 使用 `.env.example` 配置一套新环境。
- 从空数据库执行全部迁移和测试数据初始化。
- 后端测试、覆盖率和 package 全部通过。
- 前端安装、测试和 build 全部通过。
- 检查前端构建产物不包含密钥和个人服务器地址。
- 执行完整主链路：注册/登录 → 浏览 → 加购 → 试算 → 下单 → 支付 → 商家接单/出餐 → 骑手接单/取餐/送达 → 顾客确认 → 评价 → 看板核对。
- 执行异常链路：余额不足、优惠过期、库存并发、重复支付、两骑手抢单、越权访问、地图/AI 超时、取消与资产回退。
- 核对 SRS、数据库文档、OpenAPI/ApiFox、测试报告、测试日志、需求变更、AI 使用和交叉验收材料。

### 18.3 交叉验收证据

每个模块至少保存：

- 需求 ID 和验收标准。
- RED/GREEN/REFACTOR 提交 ID。
- 自动化测试类及运行结果。
- 覆盖率报告。
- 接口请求和响应样例。
- 正常、异常、权限和边界场景截图或日志。
- 发现的问题、负责人、修复提交和复测结果。
- AI 辅助使用点以及成员的人工修改和理解说明。

## 19. Definition of Done（完成定义）

一个需求只有同时满足以下条件才算完成：

- [ ] 需求 ID、规则、角色和验收标准明确。
- [ ] 接口和数据库变更已评审，无私自新增公共契约。
- [ ] 先有有效失败测试，再有功能实现提交。
- [ ] 正常、异常、权限、边界及必要并发测试通过。
- [ ] 核心接口和关键方法达到课程覆盖率要求。
- [ ] 后端分层正确，Controller 无复杂业务逻辑。
- [ ] 前端通过统一 request/service 调用，无硬编码环境地址。
- [ ] 金额、时间、状态、错误码和分页遵循统一格式。
- [ ] 数据库迁移可在空库建立完整结构。
- [ ] API 文档、README、需求追踪和测试日志已同步。
- [ ] 无密钥、真实敏感信息、调试日志和无关构建产物。
- [ ] 至少一名非作者成员完成审查和本地复测。
- [ ] 合入 `develop` 后全项目构建及主链路冒烟通过。

## 20. 开工前必须共同确认的决策

以下项目需要在第一次并行编码前明确责任人和最终选择，并写入决策记录：

1. 四个创新模块和骑手公共链路分别由谁主责、谁交叉评审。
2. `develop` 维护人和每日轮值集成人。
3. 公共异常、响应、认证、路由、状态机和数据库迁移的维护人。
4. 前端测试框架及统一的 `npm run test` 命令。
5. 数据库大版本、字符集、时区、逻辑删除字段和迁移工具。
6. API 统一响应、错误码区间、分页格式和日期格式。
7. 订单与配送完整状态表，以及每个转换的角色权限和资产回退。
8. 钱包、优惠券、积分和会员的最终冻结规则。
9. AI、语音、识图、地图的供应商、Mock 方案、预算和隐私规则。
10. 最终代码冻结日期、完整回归负责人和交叉验收安排。

确认后，所有成员在同一份决策记录中签名或留下可追踪确认。未确认的公共规则不得由单个模块成员自行假设后合入集成分支。
