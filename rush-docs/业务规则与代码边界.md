# 业务规则与代码边界

这份文档用于防止同一个业务概念在多个页面、多个接口中各写一套。新需求先找到下表中的权威位置，再修改展示层。

## 单一事实来源

| 业务事实 | 权威位置 | 前端只做什么 |
| --- | --- | --- |
| 商品价格、满减、配送费、红包、积分 | `OrderPricingService` 及数据库 | 展示后端计算结果，不提交自己算的价格 |
| 商品平台上限、库存、商家限购 | `PurchaseRules` 与 `ProductPurchasePolicy` | `cartQuantityRules.js` 只做提前反馈，后端仍须复核 |
| 购物车读写 | `CartService` | 统一通过 `services/cartService.js` 调用 |
| 登录用户和地址归属 | JWT 与 `CurrentUserService` | 统一通过 `services/addressService.js`，不上传用户 ID |
| 订单状态 | 后端 `OrderStatus` | 前端只使用 `utils/orderPresentation.js` 中的常量和分组 |
| 商家评分、销量、人均、推荐标签 | `BusinessMapper.xml` 的 `BusinessSearchColumns` 与 `BusinessRecommendationPolicy` | 首页、搜索、收藏页展示同一结果，不再自己造评分 |

## 前后端边界

- 前端可以为了体验提前置灰按钮，但权限、价格、限购、库存、状态迁移都必须由后端再验证。
- 请求体中的 `userId`、`customer`、`businessId` 都不能直接当作权限依据；后端必须用 JWT 得到当前用户，再查库确认关系。
- 接口失败要显示错误或空状态，不能在正常页面中偷偷混入模拟商品、模拟用户或随机业务数据。
- 演示数据只放在 `demo-seed.sql`、`rider-demo-seed.sql` 和 `demo-showcase-seed.sql`，页面组件不内置演示店铺或订单。

## 修改新需求的顺序

1. 先修改数据模型和后端领域规则，并补服务层测试。
2. 再通过统一的前端 `services` 封装接口。
3. 页面只引用共享常量、格式化函数和服务，不复制规则。
4. 运行 `./scripts/check-architecture.sh`、后端测试和前端构建，再用浏览器走相关角色的完整流程。

## 历史兼容层

后端目前仍保留少量旧 URL，用于避免一次性破坏学姐版项目的其他未启用页面。新代码不得再调用这些接口：

- `GET /api/carts/add`、`GET /api/carts/quantity`、`GET /api/carts/remove`
- `/api/addresses/listDeliveryAddressByUserId`、`/updateDeliveryAddress`、`/removeDeliveryAddress`

等所有可达页面都迁移完并经过回归测试后，再单独删除兼容层。
