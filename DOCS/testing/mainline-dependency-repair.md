# 主线依赖衔接修复说明

## 为什么先做这次修复

接手 lightweight-takeout-platform 的主线提交 `7596c8c` 后，实际运行 Maven 测试，发现生产代码编译阶段有 16 条错误；测试还没有开始执行。

商家代码引用了缺失的权限、订单状态、推荐规则；骑手审核控制器引用了缺失的骑手和配送服务；审批代码直接引用尚未加入的 WebSocket 实现。另有业务代码调用了当前登录模块尚未提供的管理员检查方法。

这是主线集成缺陷，不是个人资料功能的 RED。不能把“编译不过”记成新增功能的验收测试失败，也不能将后续所有功能提前导入来掩盖分工边界。本次保留已合入的登录实现和全部既有测试，不修改已经发布的提交历史。

## 改动及边界

- 补齐 AuthorityName、OrderStatus、BusinessRecommendationPolicy，并给 CurrentUserService 增加统一的管理员判断。订单状态为空时返回业务异常，而不是空指针异常。
- 补齐 RiderService 及实现，让已有骑手审批入口能连接真实数据库逻辑。审核服务本身也检查管理员权限；审核 SQL 只允许从待审核状态更新，失败时不得继续授予权限或发送成功通知。
- DeliveryService 与 DTO 是后续配送模块的接口契约，不是配送实现。当前没有该服务实现时，管理员配送异常接口明确返回 HTTP 503、错误码 FEATURE_UNAVAILABLE；不会返回空列表或假成功。后续实现 DeliveryService 并注册为 Spring 服务即可接入。
- 审批服务改为依赖 NotificationDispatcher，不再绑定某个 WebSocket 类。数据库中的审核结果通知照常保存。实时通道通过 NotificationTransport 接入，事务提交后才尝试发送，回滚不发送；实时发送失败不反过来把已提交的审批报成失败。
- **当前没有实时通知适配器。** 本次不宣称实现 WebSocket、可靠重试或实时到达。管理员新申请提醒目前不能实时推送，仍须查询申请列表。后续消息模块需要实现并注册 NotificationTransport，不能仅放入同名 WebSocket 类就认为已接通。

## 怎样验证

2026-09-07 本地实际结果：修复后后端全量测试 **109 项通过，0 失败、0 错误、0 跳过**（原有 88 项，新增 21 项）；前端登录测试 **15 项通过**，独立登录预览构建成功。商家目录、商店购物车、审批权限的三个源码契约脚本通过，但它们只检查文件与标记存在，不能替代运行时验收。完整前端构建仍失败，原因见文末。

有 JDK 17 和 Maven 的成员在 elm_bk 目录运行：

```sh
mvn test
```

所有新增集成测试使用独立 H2 内存数据库，不连接演示数据库，不要求启动配送或消息服务。其中：

- MainlineApprovalIntegrationTest 使用真实 Spring 权限/事务代理、MyBatis 和数据库，检查审核成功后状态/权限/消息一起提交，失败后回滚，重复审核不重复通知，普通用户无法调用管理员服务。
- RiderAuditCompatibilityTest 检查审核参数、拒绝原因、重复审核及并发更新失败分支。该类使用 mock，不能单独证明数据库事务正确。
- NotificationDispatcherTest 检查缺失适配器、提交后发送、回滚不发送、发送故障隔离。不是 WebSocket 网络测试，也不是消息重试测试。
- AdminDeliveryAvailabilityTest 检查缺失配送实现时的 503，以及存在实现时的转发。集成测试另行验证真实安全过滤链仍限制管理员权限。
- MainlinePolicyCompatibilityTest 检查权限判断、非法订单状态及推荐标签门槛。
- 原有登录、注册、安全和商家规则测试全部保留。

前端在 elmclient 目录运行：

```sh
npm run test:auth
npm run build:auth
```

这两个命令只验证登录相关测试和独立登录预览构建。**不能用它们代替完整前端验收。**
